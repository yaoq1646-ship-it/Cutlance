# 架构说明

本文记录 Cutlance 的关键设计决策与踩过的坑。功能列表见 [README](../README.md)。

## 1. 整体数据流

```
              ┌─────────────────────────────────────────────┐
 输入源        │  VmemInput（每路一份）                       │
 · 本地文件    │   ├─ LibVLC 解码 → 内存视频帧（BGRA）        │
 · 摄像头      │   └─ 音频 → AudioBus（可选挂接）             │
 · 采集卡      │                                             │
 · 桌面捕获    └─────────────────────────────────────────────┘
 · PPT 放映窗                 ↓ 取帧（Acquire）
 · 网络流        ┌───────────────────────────────────────────┐
 · NDI          │  Compositor（成品帧 1920×1080 BGRA）       │
                │  图层混合 → 描边/阴影 → 叠加层             │
                │  → 转场旧帧 → FTB                         │
                └───────────────────────────────────────────┘
                             ↓ swap 后锁内分发
                ┌───────────────────────────────────────────┐
                │  IProgramFrames（所有输出线的共同入口）     │
                └───────────────────────────────────────────┘
                   ↓        ↓         ↓          ↓
                RTMP推流  本地录制   NDI Sender  HDMI全屏
                (ffmpeg)  (ffmpeg)   (SDK)      (独立STA线程)
```

**核心约束：只有一帧成品。** 所有输出线消费同一份像素，因此推流画面、录制文件、副屏 HDMI 永远一致——不存在「录的和播的不一样」这类事故。

## 2. 合成器

### 2.1 图层

每个输出槽位是一个 `Compositor.Layer`，包含：

- 源（`VmemInput`）、绘制矩形（`X/Y/W/H`）、层级 `Z`
- 不透明度 `Alpha`（0–255）
- 描边（粗细 / 圆角 / 颜色）、阴影（扩散 / 浓淡）
- 填充方式 `FitMode`：0 等比内接 / 1 铺满裁切 / 2 拉伸

系统按 `Z` 排序后逐层混合，混合公式为**直通 alpha**：

```
out = src × a + dst × (1 − a)
```

> **为什么不用预乘公式？**
> 转场时旧帧是已经合成过的画面，它没有被乘过 alpha。若复用预乘公式
> `src×a + dst×(1−a)×255`，画面会发白发亮。实测这是最容易踩的坑之一。

### 2.2 描边与阴影画在成品帧上

图层在界面里是透明 Grid，WPF 的 `Border` / `DropShadowEffect` 只影响界面取景框，**推流端完全看不到**。
因此描边与阴影都在 `Compositor` 里用像素运算绘制：

- 贴**实际画面矩形**（等比内接后内缩的那块），而不是槽位外框
- 圆角描边只画环带，不整块扫描
- 阴影四周均匀、按距离平方衰减

> 判定方法：自检时把背景临时改成中灰，否则阴影画在纯黑底上根本看不出来。

### 2.3 合成顺序固定

```
图层混合 → 描边/阴影 → 叠加元素（倒计时等） → 转场旧帧 → FTB
```

新效果按此顺序插入。顺序错了会出现「叠加元素被转场吃掉」「FTB 压不黑叠加层」这类问题。

## 3. 输出通路

### 3.1 ffmpeg 管道

```
ffmpeg -nostdin -f rawvideo -pix_fmt bgra -s WxH -r fps -i pipe:0 ...
```

- 帧从 stdin 以裸 BGRA 送入，编码由 ffmpeg 完成
- 内部队列约 0.35 秒；**满了丢帧而不是阻塞**，宁可丢帧也不能让合成线程卡住
- 停止靠**关闭 stdin 触发 EOF**，而不是杀进程

### 3.2 输出级选项必须各写一遍

`-c:v` / `-c:a` 是**输出级**选项。推流和录制是同一个 ffmpeg 进程的两个输出，各自都要写一遍编码参数，否则第二个输出会退回默认编码器（实测曾出现推流静默变成 flv1 + mp3）。

> 只测「只录不推」永远发现不了这个问题。

### 3.3 分段录制

- `-f segment -segment_time N -reset_timestamps 1`，`-g` 设为 2 秒保证边界落在关键帧
- 不加 `+faststart`（分段场景无意义且增加内存开销）
- 停止时检查最后一段：**短于 1 秒且总段数 ≥2** 才删除（避免把唯一一段有效内容删掉）

### 3.4 全屏输出独立线程

HDMI 全屏窗口跑在独立的 STA 线程 + 自己的 Dispatcher 上，帧由合成器 sink 拷贝过去。

需要独立线程的原因：WPF 的 UI 线程一旦被主界面卡住（例如打开对话框、加载工程），副屏画面会跟着顿。分开后主界面卡顿不会拖累输出。

三个必须注意的点：

1. **窗口不能套带 `Icon` 的样式**：`ImageSource` 是主线程创建的，新线程读它会抛「调用线程无法访问此对象」，起窗直接失败
2. **`AddDirtyRect` 必须在 `Lock` 内**：写在外面每帧都报「图像未锁定」
3. **起窗失败时 `Dispatcher.Invoke` 会永久阻塞**：Close 前必须先判断 `HasShutdownStarted && Thread.IsAlive`

## 4. 音频通路

```
八路采集 ─┐
          ├→ 每路 volume → acompressor → alimiter ─┐
画面声音 ─┘                                        ├→ amix → 总线压缩 → 编码
                                                  ┘
```

- **角色档**：主音 0 dB / 次音 −8 dB / 背景 −14 dB，最终电平 = `音量% × 角色档增益`
- **逐路压缩**管单路忽大忽小；**总线压缩**管混完之后顶不顶 0 dB
- `acompressor` 的 `threshold` / `makeup` 单位是**线性倍数**而非 dB，且数值必须用 `InvariantCulture`，否则小数点会变成逗号导致滤镜解析失败
- `alimiter` 必须 `level=disabled`：默认的 `auto` 会把小声段抬起来，直播场景非常危险

### 4.1 混音线程绝不直接写设备

混音结果入队，每路输出一个独立写线程 + 约 1.2 秒队列。直接写会因设备缓冲抖动导致爆音。

## 5. 线程模型

| 线程 | 职责 | 约束 |
|---|---|---|
| UI 线程 | WPF 界面、鼠标钩子回调、参数变更 | **绝不在这里做重计算**；高频输入必须采样合并 |
| 合成线程 | 取帧 → 合成 → 分发 | **绝不碰 UI 控件**（读 `SelectedIndex` 也会抛异常） |
| 输出线程 | ffmpeg stdin 写入、NDI 发送 | 队列满时丢帧，不阻塞合成 |
| 全屏输出线程 | 副屏窗口 + 上屏 | 独立 Dispatcher |
| 音频写线程 | 每路独立写设备 | 队列解耦 |

### 5.1 全局鼠标钩子的性能陷阱

输出画布上覆盖着 LibVLC 的 Win32 子窗口，WPF 收不到它的鼠标事件（airspace 问题），所以图层与倒计时的拖动用 `WH_MOUSE_LL` 全局钩子实现。

**关键事实：低级鼠标钩子的回调运行在安装它的线程上，也就是 UI 线程。**

鼠标每秒会派发几百到上千条 `WM_MOUSEMOVE`。如果每条都做完整处理（走视觉树换算坐标、加锁、重算位置、更新渲染），UI 线程会被完全占满，表现为**元素抖动、跟不上手**。

解法是**采样合并**：

```
钩子回调：只用缓存的画布 origin/scale 做线性换算，存下最新坐标（几条算术）
    ↓
16 ms DispatcherTimer（Input 优先级）：取最新坐标算一次位置
```

这样无论鼠标多快，UI 都只按约 60 Hz 更新，且永远用最新位置。

**另一个陷阱：归属判定只在「按下」时做。** 如果对每条消息都判断「这一点属于哪个窗口」，鼠标一旦拖出窗口范围就会命中其它进程，导致拖动态被清掉、拖动中断。正确语义是：判定只决定**要不要开始**接管，接管之后负责到松手为止。

## 6. 工程与预设

### 6.1 工程文件

保存「整张台面」：输入源、预览排列、输出槽位（含每格绑定、几何、描边阴影、透明度、填充、去隔行）、八路混音、压缩档、倒计时牌样式、界面状态。

写入采用 `.tmp` + `File.Replace`，读取时**任何异常都当作「没有工程」**，绝不因为一个损坏字段阻断启动。

> 一个容易忽略的点：还原顺序会影响结果。例如图层添加流程内部会先按默认值计算一次音频路由，
> 因此还原完所有字段后**必须再补算一次**，否则界面显示「次音 −8 dB」而实际按主音输出。

### 6.2 布局预设

与工程文件分离：预设只记「画面怎么摆」，不含输入素材的绝对路径认领细节，可跨工程复用。

素材认领按三级匹配：路径 → 编号 + 名称 → 名称。认不到就留空，但**保留几何信息**，方便只调位置。

## 7. 失败处理原则

- **导播中绝不弹模态框**：任何错误只写状态栏 + 日志，弹框会盖住播出画面
- **错误日志三级兜底**：程序目录 → `%LOCALAPPDATA%` → `%TEMP%`
- **参数生效要重启输出**：编码器、压缩等参数改了不热更新，避免半途状态不一致
- **到点触发类事件先收尾再抛事件**：否则重入会导致连锁触发

## 8. 验证方法

见 README 的「质量保证」一节。核心原则：

> **有文件 ≠ 录到了；画面变了 ≠ 效果生效。**
> 判据必须是成品帧取样、帧数统计、`blackdetect` / `idet` 这类客观数字。
